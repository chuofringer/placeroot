# Head-to-head: PlaceRoot vs Mapbox MCP vs Google Maps MCP

[docs/benchmarks.md](benchmarks.md) measures PlaceRoot against itself. This page
measures it against the alternatives, on the two numbers an agent actually pays:
the **schema surface** every conversation carries, and the **answer size** every
call returns.

The servers compared:

- **Mapbox MCP** — [github.com/mapbox/mcp-server](https://github.com/mapbox/mcp-server),
  the category leader, and the vendor whose own GeoAI predictions name oversized
  MCP responses ("large driving-directions responses or large GeoJSON objects")
  an unsolved problem.
- **Google Maps MCP** — the archived Anthropic reference server,
  [`servers-archived/src/google-maps`](https://github.com/modelcontextprotocol/servers-archived/tree/main/src/google-maps).
  Archived and read-only, but still the shape most people picture when they
  picture a maps MCP server, so it is worth a column.

Everything below is regenerated by one command:

```bash
uv run python benchmarks/competitor_comparison.py --write
```

That rewrites only the marked section. The prose is hand-written; the numbers
never are.

## Method

- **Competitor data is vendored, not fetched.** Snapshots live under
  [`benchmarks/competitors/`](../benchmarks/competitors/) with repo, commit hash
  and capture date recorded in
  [`provenance.json`](../benchmarks/competitors/provenance.json). The test suite
  and the generator read those files and nothing else — no network at test time,
  no API keys anywhere.
- **Their schema surfaces are their real ones.** Mapbox's is the verbatim
  `tools/list` reply from their server, built from the pinned commit and run over
  stdio with a dummy token (a `tools/list` never reaches the Mapbox API). The
  archived Google server exits at startup without an API key, so its tool list is
  evaluated straight out of the literal `MAPS_TOOLS` region of its `index.ts`.
  Both capture scripts are committed in
  [`benchmarks/competitors/capture/`](../benchmarks/competitors/capture/).
- **Their answers are their real output.** Each competitor server was run over
  stdio with its upstream HTTP calls redirected to a local stub that replies with
  the vendor's *own documented example response* for that endpoint. So the text
  measured is their code's formatting, their field selection and their added
  hints — on a payload they publish themselves. No live traffic, no hand-typed
  JSON, no estimates. Where a vendor no longer publishes an example response for
  an endpoint, the cell says **not measured** rather than carrying a guess.
- **Our answers come from the committed fixtures**, through the same
  `placeroot.server` functions the MCP server exposes, reusing
  `benchmarks/token_efficiency.py`'s scenario machinery so the two benchmarks
  cannot drift apart — and they are then **snapshotted too**, into
  [`benchmarks/competitors/placeroot_answers.json`](../benchmarks/competitors/placeroot_answers.json),
  which records the platform they were captured on. Routing and geometry do
  floating-point work whose last digits differ between operating systems, and a
  digit is a character, and characters are what chars/4 counts: a live rerun of
  these scenarios lands a token or two away on Linux from where it lands on
  macOS. Publishing from a snapshot is what lets the page be drift-guarded byte
  for byte everywhere instead of only on the machine that last regenerated it.
  The live run still happens in the test suite, as a tolerance check that fails
  if the snapshot drifts from what the code now answers. Only PlaceRoot's
  *schema surface* is read live — it is platform-independent text, and reading
  it live is what makes a newly added tool move this page.
- **One ruler for everyone.** Token counts are the chars/4 heuristic that
  `placeroot.budget.estimate_tokens` already uses to enforce PlaceRoot's own
  response budget, applied identically to all three servers. Unlike
  `token_efficiency.py`, this script never opportunistically upgrades to
  `tiktoken`: a comparison needs one ruler, and it needs to give the same answer
  on every machine so the committed page can be drift-guarded byte for byte.
  chars/4 undercounts dense JSON, so treat every figure as a floor.

## Honest limitations

Read this paragraph before quoting any number above it.

Mapbox and Google are **live-data services**. They know today's traffic, current
opening hours, ratings and reviews, business status, and they geocode against
proprietary address data with worldwide coverage. PlaceRoot is **keyless and
static**: it answers from a pinned Overture Maps release, has no traffic model,
no hours, no ratings, and its `distance_matrix` is a straight-line haversine
calculation rather than the road-network travel times Mapbox's and Google's
matrix APIs return. Anyone comparing these servers on capability rather than on
token cost should reach for theirs. The claim here is narrower and falsifiable:
for the spatial questions PlaceRoot *does* answer, it answers them in fewer
tokens.

The two costs also behave differently, and conflating them would be a cheat.
**Schema tokens are paid once per conversation**, whether or not a spatial
question is ever asked — that is the number that punishes a large tool surface.
**Answer tokens are paid per call** — that is the number that punishes verbose
payloads. A server can win one and lose the other, and the generated section
below reports both rather than a blended score.

Finally, vendor documentation abridges long payloads: Mapbox's published
isochrone example replaces every polygon ring with a placeholder string, and its
search examples carry a single feature. Their answer-size figures are therefore
floors too, and understate what a real response costs. The generated section
restates each of these caveats next to the numbers they qualify.

### What these numbers are not

- Vendor documentation abridges long payloads. The Mapbox isochrone example replaces every polygon ring with the literal string "arrays of longitude, latitude coordinates", and its search examples carry a single feature and a "{mapbox_id}" placeholder. Competitor answer sizes below are therefore floors, not typical values — a real isochrone or a ten-result search is much larger.
- The only Mapbox Directions example response their reference publishes is an EV route with charging stops, and it carries no step-by-step geometry. A real turn-by-turn response with geometry is far larger.
- The nearest_coffee row is the least comparable in the table and should not be read as a win or a loss: PlaceRoot returns ten ranked places, while Mapbox's published category-search example contains one POI. Their cell is roughly a per-result cost; ours is a ten-result answer.
- Mapbox's search, geocode and category tools return formatted plain text rather than JSON, which is a real compaction choice on their part and is reflected in the '(text)' cells. Their routing, isochrone and matrix tools return upstream JSON, pretty-printed.
- **Google Maps MCP (archived), not measured**: nearest_coffee, route_a_to_b, isochrone_15min, matrix_3x3. Google retired the legacy web-service reference pages this server calls, so no documented example response is available for Places Text Search, Directions or Distance Matrix, and their server has no isochrone tool at all. Rather than estimate, these are reported as not measured.

## Refreshing the snapshots

The capture scripts need network access and Node, and are run by hand — never by
CI, never by the tests:

```bash
# competitor sources, read-only
git clone https://github.com/mapbox/mcp-server.git
(cd mcp-server && npm ci && npm run build)
git clone https://github.com/modelcontextprotocol/servers-archived.git
(cd servers-archived/src/google-maps && npm install && npm run build)

# refresh the vendored snapshots
python benchmarks/competitors/capture/extract_doc_examples.py
MAPBOX_MCP_DIR=./mcp-server \
  node benchmarks/competitors/capture/capture_mapbox_tools_list.mjs
GOOGLE_MAPS_MCP_SRC=./servers-archived/src/google-maps \
  node benchmarks/competitors/capture/capture_google_maps_tools_list.mjs
MAPBOX_MCP_DIR=./mcp-server GOOGLE_MAPS_MCP_SRC=./servers-archived/src/google-maps \
  node benchmarks/competitors/capture/capture_answers.mjs

# then update commit hashes and dates in benchmarks/competitors/provenance.json
uv run python benchmarks/competitor_comparison.py --write

# re-snapshot our own answers as well (records the capturing platform), after a
# change to what a tool returns:
uv run python benchmarks/competitor_comparison.py --capture-answers --write
```
